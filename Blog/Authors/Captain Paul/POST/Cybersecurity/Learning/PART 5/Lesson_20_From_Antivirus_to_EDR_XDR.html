PART 5 · Lesson 1 EDR · XDR Endpoint Security

From Antivirus to EDR and XDR

Captain Paul
Maritime Cybersecurity · IACS UR E26/E27
September 2026
🎯 Lesson Objective

After this lesson you can explain why signature-based antivirus is insufficient against modern threats, describe how Endpoint Detection and Response (EDR) improves on AV through behavioural monitoring and telemetry, explain the concept of Extended Detection and Response (XDR) and how it correlates signals across domains, and understand why maritime vessel workstations need EDR-class protection rather than legacy AV.

For most of the 1990s and 2000s, antivirus was the primary endpoint security control. It worked on a simple principle: collect samples of known malware, extract unique byte patterns (signatures), and scan incoming files and processes for those signatures. If a file matches a signature, block it. If it does not match, allow it. This model worked reasonably well when malware was relatively simple and circulated slowly.

Modern attackers broke this model in two ways. First, they developed techniques to evade signature detection: packing and obfuscating malware so its byte pattern changes with each instance (polymorphic malware), using legitimate system tools like PowerShell and WMI to execute malicious code without dropping a detectable file (living-off-the-land), and exploiting zero-days where no signature exists. Second, the sheer volume and velocity of new malware made comprehensive signature coverage impossible — AV vendors cannot write signatures fast enough to cover every new variant.

EDR (Endpoint Detection and Response) addresses this by shifting from signature matching to behavioural monitoring. Instead of asking 'does this file match a known bad pattern?', EDR asks 'is this process behaving in a way that is consistent with malicious activity?' — launching a child process that connects to an external IP, accessing sensitive registry keys, injecting code into another process, encrypting files at high speed. These behaviours are malicious regardless of whether the file that triggers them has a known signature.

1. The Limits of Signature-Based AV

1. The Limits of Signature-Based AV
1
Signature Detection and its Failure Modes

Signature-based AV requires a sample of a malicious file to create a detection. Zero-days, polymorphic malware, and fileless attacks (which run entirely in memory without a detectable file) all evade signature detection by design. Nation-state attackers and sophisticated ransomware groups test their payloads against the major AV products before deployment, iterating until they achieve low detection rates. The 'arms race' between AV vendors and attackers has consistently favoured the attackers for more than a decade.

2
Living-off-the-Land (LotL) Attacks

Living-off-the-land attacks use legitimate operating system tools — PowerShell, WMI, certutil, mshta, regsvr32 — to execute malicious code. Because these tools are part of Windows and routinely used by administrators, their execution does not trigger AV signatures. A PowerShell command that downloads and executes a payload from a remote server is indistinguishable from a legitimate admin script to signature-based AV. LotL is the dominant technique in ransomware and APT campaigns.

3
The Detection Gap

Studies consistently show that signature-based AV misses 10-30% of novel malware samples. For targeted attacks — where the attacker has specifically crafted their payload to evade the target's AV — detection rates can be near zero. In maritime environments where AV is often out of date (vessels with infrequent connectivity cannot update signatures in real time), the detection gap is even larger. Legacy AV provides a false sense of security against modern threats.

2. EDR — Behavioural Detection and Response

2. EDR — Behavioural Detection and Response
1
Continuous Monitoring and Telemetry

EDR agents run continuously on the endpoint, collecting telemetry: every process that starts (with its parent process, command line, and hash), every file created or modified, every registry key accessed, every network connection initiated, every memory allocation. This telemetry stream is sent to a cloud backend or on-premises server for real-time analysis and historical retention. Investigators can query this telemetry to reconstruct exactly what happened on an endpoint during an incident — days, weeks, or months after the fact.

2
Behavioural Detection Rules

EDR detection rules fire on behavioural patterns rather than signatures: PowerShell executing encoded commands (T1059.001), a process spawning cmd.exe from a browser (browser exploitation indicator), a ransomware-like pattern of mass file encryption with extension change, credential dumping from LSASS memory (T1003.001). These rules fire on behaviour that is suspicious regardless of the specific malware involved, providing detection capability against novel threats.

3
Response Capabilities

EDR's 'R' — Response — differentiates it from traditional AV. When a threat is detected, the EDR can: isolate the endpoint from the network (preventing lateral movement while preserving remote management), kill malicious processes, quarantine or delete malicious files, roll back file system changes (undoing ransomware encryption in some cases), and provide the investigator with a forensic timeline. Remote response capabilities mean an incident on a vessel can be triaged and contained from the shore-based SOC without physical access to the device.

4
Maritime EDR Considerations

Bridge workstations running ECDIS, GMDSS, and other navigation applications have specific EDR deployment considerations: the EDR agent must not interfere with safety-critical software operation, must function during satellite connectivity outages (local detection, queued telemetry), and must be validated against the navigation software vendor's compatibility requirements. IACS UR E27 Type Approval for navigation systems increasingly includes cybersecurity testing that validates EDR compatibility.

3. XDR — Extended Detection and Response

3. XDR — Extended Detection and Response
1
XDR Concept

Extended Detection and Response (XDR) extends the EDR concept beyond the endpoint to correlate signals across multiple domains: endpoint, network, email, cloud, and identity. An XDR platform sees that a phishing email delivered a malicious attachment (email layer), a user opened it and a suspicious process spawned (endpoint layer), that process connected to a C2 server (network layer), and then used the compromised credentials to access a cloud service from an unusual location (identity and cloud layer). No single domain sees the complete attack; XDR correlates across all of them to produce a unified incident.

2
Native XDR vs Open XDR

Native XDR platforms are built by a single vendor whose products share a common telemetry schema and investigation interface — Microsoft Defender XDR, CrowdStrike Falcon platform, SentinelOne Singularity. Open XDR platforms ingest telemetry from multiple vendors' products into a common correlation engine. Native XDR provides the tightest integration; open XDR provides flexibility for organisations with diverse vendor environments. Both approaches deliver better cross-domain correlation than siloed point products.

3
Maritime XDR Application

For a shipping company with Microsoft 365 for corporate email and collaboration, Defender for Endpoint on vessel workstations, and Defender for Office 365 for email security, Microsoft Defender XDR provides native cross-domain correlation across all three layers. A phishing email targeting a vessel officer, a malicious document opened on the ship's workstation, and a subsequent credential theft attempt are correlated into a single incident — visible in one investigation interface, with automated containment available from the shore-based SOC.

✍️ Author Insight — From the Field
Captain Paul · Maritime Cybersecurity Consultant · IACS UR E26/E27

During E26 CRSI assessments, the endpoint security question on vessels almost always reveals the same finding: Windows Defender (basic, built-in AV) or a legacy AV product that has not received updates since the last port call. Neither provides meaningful protection against the living-off-the-land PowerShell attacks and commodity ransomware that currently dominate maritime cyber incidents. The argument that 'vessel workstations are isolated and therefore lower risk' underestimates the threat — crew internet access, USB devices from third-party technicians, and VSAT-connected management interfaces all provide attack paths to vessel workstations that are not exposed to the isolated OT network myth. EDR deployment on bridge and engine room workstations is now a minimum acceptable standard for vessels operating under IACS UR E26.

Practical first step: Validate your EDR deployment against your navigation software vendor's compatibility matrix before rollout. CrowdStrike, SentinelOne, and Microsoft Defender for Endpoint all maintain compatibility lists for maritime navigation software. Deploy in monitor-only mode first, confirm no interference with navigation application performance over a two-week observation period, then move to prevention mode. This approach eliminates the safety-vs-security conflict that is the most common objection to EDR deployment on bridge systems.

✅ Key Takeaways — Lesson 20
  • Signature-based AV cannot detect zero-days, polymorphic malware, or fileless/living-off-the-land attacks — the dominant techniques in modern maritime cyber incidents.
  • EDR monitors endpoint behaviour continuously — every process, file, registry, and network event — enabling detection of malicious activity based on behaviour rather than known signatures.
  • EDR response capabilities (network isolation, process kill, file quarantine, forensic timeline) enable remote incident containment on vessels from a shore-based SOC without physical access.
  • XDR extends correlation across multiple domains (endpoint, email, network, identity, cloud), enabling detection of multi-stage attacks that are invisible when viewed through any single domain lens.
  • EDR deployment on vessel workstations requires compatibility validation with navigation software vendors — an increasingly standard part of IACS UR E27 Type Approval cybersecurity requirements.
  • IACS UR E26 requires security controls on vessel systems; EDR-class endpoint protection is the minimum standard for vessel bridge and engine room workstations connected to any network.
