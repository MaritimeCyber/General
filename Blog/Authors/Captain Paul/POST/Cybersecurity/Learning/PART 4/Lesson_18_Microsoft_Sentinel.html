PART 4 · Lesson 3 Microsoft Sentinel KQL · Cloud SIEM

Microsoft Sentinel

Captain Paul
Maritime Cybersecurity · IACS UR E26/E27
September 2026
🎯 Lesson Objective

After this lesson you can describe Microsoft Sentinel's architecture and pricing model, explain how data connectors, analytics rules, workbooks, and playbooks work together, write basic KQL queries for security investigation, identify the built-in content packages most relevant to maritime cybersecurity, and understand how Sentinel integrates with Microsoft Defender for Endpoint and Microsoft 365 Defender.

Microsoft Sentinel is a cloud-native Security Information and Event Management (SIEM) and Security Orchestration, Automation, and Response (SOAR) platform built on Azure. Launched in 2019, it has become one of the dominant enterprise SIEM platforms globally — particularly for organisations already in the Microsoft ecosystem, where its deep integration with Microsoft 365, Azure Active Directory, and Microsoft Defender provides out-of-the-box coverage that would take months to build on a traditional SIEM.

For maritime organisations, Sentinel's Microsoft 365 integration is particularly valuable. Most shipping companies run Microsoft 365 for email, collaboration, and identity management. Connecting Sentinel to Microsoft 365 immediately provides: sign-in logs from Azure AD, email security alerts from Defender for Office 365, and endpoint alerts from Defender for Endpoint. A maritime operator who has made no prior security tool investment but has a Microsoft 365 subscription already has a foundation for meaningful monitoring.

Sentinel's pricing model — consumption-based, charged per gigabyte of data ingested — changes the economics of SIEM deployment. Unlike traditional SIEMs with large upfront licensing costs, Sentinel scales with the organisation's actual log volume. For a shipping company monitoring a fleet of 20 vessels, this can be significantly more cost-effective than a traditional SIEM deployment, though log volume management (deciding what to ingest) becomes a critical cost-control discipline.

1. Sentinel Architecture

1. Sentinel Architecture
1
Log Analytics Workspace

Sentinel is built on top of Azure Log Analytics, which provides the underlying data ingestion, storage, and query engine. All ingested data is stored in a Log Analytics Workspace and queried using Kusto Query Language (KQL). The Workspace is the unit of Sentinel deployment — multiple Workspaces can be used for different environments (e.g., separate Workspaces for fleet operations and corporate IT) but cross-Workspace query is supported.

2
Data Connectors

Data connectors link log sources to the Sentinel Workspace. Microsoft's first-party connectors — Azure AD, Microsoft 365 Defender, Defender for Endpoint, Azure Activity — connect with a single click. Third-party connectors cover hundreds of common security products (Cisco, Palo Alto, Fortinet). For maritime OT systems and vessel-specific sources, custom connectors are built using the Azure Monitor Agent, syslog forwarding, or the Sentinel REST API.

3
Analytics Rules

Analytics rules are the detection engine. Scheduled analytics rules run KQL queries on a defined interval (every 5 minutes, every hour) and generate alerts when the query returns results. Fusion rules use machine learning to correlate low-fidelity signals into high-confidence composite alerts — reducing alert volume while maintaining detection coverage. Near-real-time (NRT) rules provide sub-minute latency for the highest-priority detections.

4
Workbooks and Dashboards

Sentinel Workbooks are Azure Monitor dashboards built with KQL queries, providing visualisations for security operations: login trends, alert distribution, geographic access maps, fleet monitoring dashboards. Workbooks are the operational interface for SOC analysts — a well-designed maritime fleet monitoring workbook shows vessel connectivity status, recent alerts by vessel, and log ingestion health for each ship's sensors in a single view.

2. KQL — Kusto Query Language Basics

2. KQL — Kusto Query Language Basics
1
KQL Fundamentals

KQL uses a pipe-based syntax: start with a table name, then chain operators separated by the pipe character (|). The most common operators are: where (filter rows), project (select columns), summarize (aggregate), extend (add calculated columns), join (combine tables), and order by (sort results). A query that finds all failed sign-ins from a specific country in the last 24 hours: `SigninLogs | where TimeGenerated > ago(24h) | where ResultType != 0 | where Location == 'RU' | project TimeGenerated, UserPrincipalName, IPAddress, ResultDescription`

2
Writing Detection Rules in KQL

A Sentinel analytics rule is a KQL query that returns alert-worthy results. A brute force detection rule: `SecurityEvent | where EventID == 4625 | summarize FailedAttempts = count() by Account, IpAddress, bin(TimeGenerated, 10m) | where FailedAttempts > 10`. When this query returns rows (accounts with 10+ failed logons in a 10-minute window), Sentinel creates an incident. KQL's time-series and aggregation functions make it well-suited to threshold-based and pattern-matching detection.

3
Threat Hunting with KQL

Threat hunters use KQL to search for indicators of compromise and ATT&CK techniques across historical log data without waiting for a rule to fire. A hunter investigating potential lateral movement searches for: `SecurityEvent | where EventID == 4624 | where LogonType == 3 | summarize count() by TargetUserName, IpAddress | where count_ > 5`. KQL's ability to search across all ingested data — terabytes, if necessary — makes it powerful for post-incident forensics as well as proactive hunting.

4
Maritime KQL Use Cases

Purpose-built maritime KQL queries for vessel monitoring: detecting VSAT management interface logons from non-whitelisted IP ranges; alerting on vessel OT network outbound connections; detecting USB storage device insertion events on bridge workstations; monitoring for ECDIS software process termination or restart. These queries form the foundation of a maritime vessel monitoring use case library in Sentinel.

3. Sentinel Playbooks and SOAR

3. Sentinel Playbooks and SOAR
1
Playbooks (Logic Apps)

Sentinel playbooks are automated response actions triggered when an incident is created or updated. Built on Azure Logic Apps, playbooks can: send a Teams notification when a high-severity alert fires, automatically enrich an incident with geolocation data for each IP address, isolate a compromised endpoint via the Defender for Endpoint API, or create a ticket in the service desk system. Playbooks execute in seconds, providing automated tier-1 enrichment and response that reduces the time between alert and action.

2
Content Hub

The Sentinel Content Hub is a marketplace of pre-built solutions — data connectors, analytics rules, workbooks, and playbooks — for hundreds of technology products and threat scenarios. Solutions for Microsoft 365, Defender XDR, and common network devices are available out-of-the-box. For maritime, the Content Hub provides a starting point: deploy the Microsoft 365 solution, the Defender for Endpoint solution, and the common network device solutions, then layer maritime-specific rules on top.

3
Sentinel and Defender XDR Integration

Microsoft Defender XDR (Extended Detection and Response) — covering endpoints (Defender for Endpoint), email (Defender for Office 365), identity (Defender for Identity), and cloud apps (Defender for Cloud Apps) — integrates natively with Sentinel. Sentinel can ingest all Defender XDR alerts and incidents, correlate them with logs from other sources, and provide a unified investigation experience. For maritime organisations using Microsoft's security stack, this integration provides broad coverage across the IT environment with minimal configuration.

✍️ Author Insight — From the Field
Captain Paul · Maritime Cybersecurity Consultant · IACS UR E26/E27

During E26 CRSI assessments of Microsoft 365 environments, Sentinel deployment is often the fastest path to meaningful monitoring capability. A maritime organisation with Microsoft 365 E5 (which includes Defender for Endpoint, Defender for Office 365, and Defender for Identity) can deploy Sentinel and connect all three in an afternoon — immediately providing detection coverage for endpoint threats, phishing attacks, and identity-based attacks that was previously zero. The gap that remains is vessel OT monitoring: Sentinel has no out-of-the-box connector for ECDIS, AIS, or vessel network equipment. Custom connectors require development effort. But the IT coverage alone — shore-based systems, email, cloud services — is a significant security improvement over the baseline of no monitoring, and provides the SOC infrastructure on which vessel monitoring can be built incrementally.

Practical first step: If your organisation has Microsoft 365 Business Premium or E3/E5, you can deploy Sentinel and connect Microsoft 365 Defender today. Enable the Microsoft 365 Defender connector, activate the Scheduled Analytics Rules from the Microsoft 365 solution content package, and you immediately have detection coverage for common attack scenarios. The ingestion cost for a small maritime operator is typically under USD 500/month — a fraction of the cost of a managed SOC contract.

✅ Key Takeaways — Lesson 18
  • Microsoft Sentinel is a cloud-native SIEM/SOAR built on Azure Log Analytics, with consumption-based pricing and deep native integration with Microsoft 365 and Defender products.
  • Data connectors link log sources to Sentinel; Analytics Rules (KQL queries run on a schedule) generate alerts and incidents when detection conditions are met.
  • KQL is Sentinel's query language — a pipe-based syntax that enables complex time-series correlation, aggregation, and threat hunting across petabyte-scale log data.
  • Playbooks (Azure Logic Apps) automate response actions — alert enrichment, endpoint isolation, team notification — reducing time-to-response from minutes to seconds.
  • The Content Hub provides pre-built solutions for common technology products; maritime operators should start with Microsoft first-party solutions and layer vessel-specific analytics rules on top.
  • For maritime organisations already in the Microsoft ecosystem, Sentinel provides the fastest path to functional monitoring capability — IT coverage is immediate; OT vessel monitoring requires custom connector development.
