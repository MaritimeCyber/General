SIEM: Turning Logs into Security Intelligence

Captain Paul
Maritime Cybersecurity · IACS UR E26/E27
September 2026
🎯 Lesson Objective

After this lesson you can explain how a SIEM ingests, normalises, and indexes log data, describe the structure of a SIEM detection rule and the concept of correlation, distinguish between rule-based detection and behaviour analytics (UEBA), explain what a use case library is and how it maps to ATT&CK, and understand the specific log sources and parsing challenges in a maritime vessel environment.

A firewall generates thousands of log entries per hour. A server generates tens of thousands. An enterprise network generates hundreds of millions of log events per day. Without a system to collect, organise, and analyse those logs, they are useless for security — a record of every event that occurred, all of them equally invisible. The SIEM's job is to turn that firehose of raw log data into security intelligence: prioritised, contextualised alerts that tell an analyst exactly where to look.

The SIEM does this through three core capabilities. First, data ingestion and normalisation — collecting logs from hundreds of different sources, each with their own format, and converting them into a consistent schema that can be searched and correlated. Second, correlation — applying rules that look across multiple log sources to identify patterns of activity that are suspicious when viewed together, even if each individual event is benign. Third, alerting — surfacing the highest-priority correlated events as alerts for human review.

Modern SIEMs have extended far beyond rule-based correlation. Machine learning models now establish baselines of normal behaviour for each user and device (User and Entity Behaviour Analytics — UEBA) and alert when behaviour deviates from the baseline, even without a matching rule. Cloud-native SIEMs like Microsoft Sentinel and Splunk Cloud handle petabyte-scale ingestion with built-in threat intelligence enrichment and AI-assisted investigation.

1. Log Ingestion and Normalisation

1. Log Ingestion and Normalisation
1
Log Sources and Connectors

A SIEM ingests logs from every security-relevant source in the environment: firewalls, routers, servers (Windows Event Logs, Linux syslog), endpoints (EDR telemetry), applications (web servers, databases, authentication systems), cloud services (Azure AD sign-in logs, AWS CloudTrail), and email gateways. Each source connects to the SIEM via an agent (software installed on the source), an API connector, or syslog forwarding. The SIEM's connector library determines which sources can be integrated out-of-the-box versus requiring custom parsing.

2
Normalisation and Parsing

Every log source generates events in its own format. A Windows security event has a different structure than a Cisco firewall log, which has a different structure than an AWS CloudTrail record. Normalisation converts all of these into a common schema — typically based on standards like Common Event Format (CEF) or the Elastic Common Schema (ECS) — so that a rule searching for 'failed logon followed by successful logon from a different IP' works regardless of whether the logon events came from a Windows server or an AWS console.

3
Indexing and Retention

Normalised log data is indexed for fast search. The SIEM's storage architecture must balance ingestion volume, search performance, and retention period. Many regulatory frameworks require 90 days to 1 year of log retention. Cloud SIEMs increasingly use tiered storage — hot storage (expensive, fast, for recent data) and cold storage (cheap, slow, for historical data) — to manage cost at scale.

4
Maritime Log Challenges

Vessel systems — ECDIS, AIS, VDR (Voyage Data Recorder), GMDSS — generate logs in proprietary formats, often with no standard connector available. Custom parsers must be developed for each system. VSAT connectivity limits the volume of logs that can be transmitted to a shore-based SIEM in real time. On-vessel log aggregators that buffer, compress, and prioritise before transmission are a common architectural approach.

2. Detection — Rules, Correlation, and Analytics

2. Detection — Rules, Correlation, and Analytics
1
Rule-Based Correlation

Detection rules define conditions that, when matched, generate an alert. A simple rule: 'alert if a user account has 5 or more failed logon attempts in 60 seconds' (brute force detection). A correlated rule: 'alert if a user account has 5 or more failed logon attempts followed by a successful logon from a new geographic location within 10 minutes' (credential stuffing with success). Rules that correlate events across multiple sources and time windows are the core of SIEM detection capability.

2
Use Case Library and ATT&CK Mapping

A use case library is a catalogue of detection rules, each mapped to a specific threat scenario and an ATT&CK technique. A mature SOC maintains a use case library of hundreds of rules covering the highest-priority ATT&CK techniques for their environment. Each rule includes a description, the data sources required, the ATT&CK mapping, the expected false positive rate, and the investigation procedure when it fires. Use case libraries are built iteratively — starting with the highest-impact, lowest-noise rules and expanding over time.

3
UEBA — Behaviour Analytics

User and Entity Behaviour Analytics (UEBA) establishes a baseline of normal behaviour for each user and device — typical logon hours, typical data access volumes, typical network connections — and alerts when behaviour deviates. UEBA detects threats that have no rule: a legitimate user account that has been compromised and is now accessing unusual resources at unusual times generates a UEBA alert even if the attacker's specific technique has no matching signature.

4
Alert Fatigue and Tuning

A poorly tuned SIEM generates thousands of false positive alerts per day, overwhelming analysts and causing real alerts to be missed. Alert tuning — adjusting rule thresholds, adding suppression conditions for known-benign activity, and retiring rules that generate too much noise — is an ongoing SOC function. The target is a manageable daily alert queue where the vast majority of alerts warrant investigation, not a firehose of noise that leads analysts to ignore the alert channel entirely.

3. SIEM Investigation and Response Workflow

3. SIEM Investigation and Response Workflow
1
Alert Triage

When a SIEM rule fires, a Tier 1 analyst reviews the alert. Triage determines: Is this a true positive or false positive? What is the severity? Is further investigation required? The analyst examines the raw log events that triggered the rule, enriches them with context (is this user account known? is this IP address malicious according to threat intel?), and either closes the alert as a false positive or escalates to Tier 2 for investigation.

2
Investigation and Pivot

Tier 2 investigation involves pivoting across the SIEM data lake — searching for related events around the same user, device, or time window. What did this user do before and after the suspicious event? What other devices communicated with this IP address? Investigation turns a single alert into a timeline of the attacker's activity, establishing scope (which systems were accessed), impact (what data was exfiltrated), and the initial access vector.

3
Case Management and Reporting

Confirmed incidents are documented in a case management system (often integrated with the SIEM or a dedicated platform like Jira Service Management or ServiceNow) with the full timeline, evidence, actions taken, and lessons learned. Case data feeds into reporting — weekly/monthly SOC metrics for management — and continuous improvement — which new detection rules did this incident suggest?

✍️ Author Insight — From the Field
Captain Paul · Maritime Cybersecurity Consultant · IACS UR E26/E27

During E26 CRSI assessments, the SIEM conversation almost always surfaces the same fundamental gap: the log sources that matter most for vessel security — ECDIS, VSAT management interface, OT network switches — either generate no security-relevant logs or generate them in formats no SIEM connector knows how to parse. The result is a SIEM that monitors the vessel's Windows workstations reasonably well and has essentially no visibility into the systems that pose the highest consequence risk. Building the parser library for vessel-specific systems — a custom ECDIS log parser, a VSAT syslog normaliser — is unglamorous engineering work, but it is the prerequisite for any meaningful vessel monitoring capability.

Practical first step: Start your SIEM use case library with four rules that every maritime operator should have: (1) Successful logon to VSAT management interface from an IP address not in your shore office range. (2) USB storage device inserted on a bridge workstation. (3) ECDIS application crash or unexpected restart. (4) Any outbound connection from the vessel OT network to an internet IP address. These four rules alone will detect the most common maritime cyber attack vectors and generate very few false positives.

✅ Key Takeaways — Lesson 17
  • The SIEM collects logs from across the environment, normalises them into a common schema, applies correlation rules to detect threats, and surfaces prioritised alerts for analyst review.
  • Detection rules range from simple threshold rules (5 failed logons) to complex multi-source correlated rules (failed logons followed by a new geographic success) that detect multi-step attack patterns.
  • UEBA extends detection beyond rules by establishing behavioural baselines and alerting on anomalous deviation — catching threats that have no signature.
  • Alert tuning is critical: an over-alerting SIEM creates fatigue that causes analysts to miss real incidents; the goal is a high-fidelity alert queue where every alert warrants investigation.
  • Maritime vessel environments present unique SIEM challenges: proprietary log formats requiring custom parsers, bandwidth-constrained log transmission, and OT systems with no native SIEM connector support.
  • The most impactful maritime SIEM use cases focus on vessel access control (VSAT login monitoring), physical security (USB detection), and OT integrity (navigation system restart, unexpected outbound connections from OT network).
