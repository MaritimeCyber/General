PART 4 · Lesson 4 Splunk SPL · SIEM · ES

Splunk for Security Operations

Captain Paul
Maritime Cybersecurity · IACS UR E26/E27
September 2026
🎯 Lesson Objective

After this lesson you can describe Splunk's architecture and deployment models, write basic SPL searches for security investigation, explain what Splunk Enterprise Security (ES) adds over the base Splunk platform, describe Splunk SOAR and its role in automated incident response, and understand the trade-offs between Splunk and Microsoft Sentinel for maritime SOC deployments.

Splunk is the platform that defined the modern SIEM category. Founded in 2003 and launched as a log management tool, it grew into the dominant security analytics platform through its combination of a powerful, flexible search language (SPL — Search Processing Language), an open data model that ingests almost any log format, and an extensive ecosystem of apps and integrations. For much of the 2010s, 'SIEM' and 'Splunk' were nearly synonymous in enterprise security operations.

Splunk Enterprise Security (Splunk ES) is the security-focused overlay on top of the base Splunk platform, providing pre-built security dashboards, notable events (Splunk's term for alerts), correlation searches (detection rules), asset and identity management, and threat intelligence integration. Splunk SOAR (formerly Phantom) provides the automation and response layer. Together, Splunk ES and SOAR form a full SIEM/SOAR stack comparable to Microsoft Sentinel.

The maritime security operations question — Splunk or Sentinel? — does not have a universal answer. Organisations with existing Splunk investments and on-premise or hybrid infrastructure often find Splunk's flexibility and deployment options better suited to their architecture. Microsoft-centric organisations with cloud-first strategies often find Sentinel's native integrations and consumption pricing more cost-effective. Both platforms can support maritime vessel monitoring with appropriate custom development.

1. Splunk Architecture and SPL

1. Splunk Architecture and SPL
1
Indexers, Search Heads, and Forwarders

Splunk's distributed architecture separates data collection (Forwarders — lightweight agents that send data to Splunk), data storage and indexing (Indexers — process and store log data as time-series events), and search execution (Search Heads — receive search queries, distribute them to Indexers, and aggregate results). Heavy Forwarders can pre-process and filter data before sending it to the Indexers. In a maritime deployment, vessel-based Heavy Forwarders aggregate vessel logs, compress them, and forward over VSAT to shore-based Indexers.

2
Splunk Processing Language (SPL)

SPL is a powerful, pipe-based search language. A basic search: `index=main sourcetype=WinEventLog EventCode=4625 | stats count by user, src_ip | where count > 5`. SPL's strength is its flexibility — virtually any transformation, aggregation, or visualisation is achievable through SPL. Key commands: search (filter), stats (aggregate), eval (calculate), rex (extract fields with regex), transaction (group related events into sessions), lookup (enrich events from external data).

3
Data Onboarding

Splunk's open data model accepts almost any log format through: pre-built Add-ons (TA-splunk-addon-for-windows, TA-cisco-asa, and 2,000+ others in Splunkbase), Syslog-NG/rsyslog forwarding for standard syslog sources, the HTTP Event Collector (HEC) API for application log shipping, and custom source type configurations with SPL-based field extraction. For vessel OT systems with proprietary log formats, custom source types with regex-based field extraction are the standard approach.

4
Deployment Models

Splunk can be deployed on-premises (self-managed), in the cloud (Splunk Cloud Platform — SaaS), or in a hybrid model with on-premises Indexers and cloud Search Heads. On-premises deployment gives full control over data residency and network architecture — relevant for maritime organisations with data sovereignty requirements or low-bandwidth vessel environments. Splunk's licensing model (historically based on daily ingest volume) can be expensive at high log volumes; the newer Splunk Workload Pricing model provides more predictable costs.

2. Splunk Enterprise Security

2. Splunk Enterprise Security
1
Notable Events and Risk-Based Alerting

Splunk ES introduces Notable Events — the ES term for security alerts generated by correlation searches. Risk-Based Alerting (RBA), a key Splunk ES capability, assigns risk scores to individual users and systems based on lower-confidence detections, then generates a Notable Event only when a risk score threshold is crossed. This dramatically reduces alert volume — individual low-confidence detections (a single failed logon, a slightly unusual process) are recorded but do not generate alerts; only the accumulation of risk does.

2
Correlation Searches

Correlation searches are SPL queries that run on a schedule and generate Notable Events when their results meet defined conditions. Splunk provides hundreds of pre-built correlation searches mapped to the MITRE ATT&CK framework. Maritime-relevant examples: 'Brute Force Access Behavior Detected or Multiple Disabled Accounts', 'Processes Launching Netsh', 'Excessive DNS Failures'. These searches are a starting point — they should be reviewed, tuned, and supplemented with maritime-specific searches.

3
Asset and Identity Framework

Splunk ES maintains an Asset and Identity database — a record of every known device and user in the environment, with attributes (criticality, category, owner, physical location). When a Notable Event references a device or user, Splunk ES automatically enriches it with Asset/Identity context: this device is on the bridge of Vessel X, it is classified as High criticality, its owner is the IT department. For maritime, populating the Asset database with vessel-specific information (which device is on which vessel, what is its function) transforms raw alerts into operationally meaningful context.

4
Threat Intelligence Management

Splunk ES includes a Threat Intelligence Management framework that ingests threat intel feeds (STIX/TAXII, CSV), normalises them, and automatically applies them to incoming events — flagging connections to known malicious IPs, file hashes matching known malware, and domains associated with threat actors. The M-ISAC (Maritime ISAC) provides sector-specific threat intel in STIX/TAXII format that integrates directly with Splunk's framework.

3. Splunk SOAR and Maritime Considerations

3. Splunk SOAR and Maritime Considerations
1
Splunk SOAR (formerly Phantom)

Splunk SOAR provides automated playbook execution, case management, and integration with hundreds of security tools through its app ecosystem. SOAR playbooks respond to incidents automatically: when a phishing email is detected, the playbook extracts URLs, queries threat intelligence, blocks the sender, and notifies the security team — in seconds, without analyst involvement. For high-alert-volume maritime operations, SOAR is critical for handling the tier-1 triage workload that would otherwise overwhelm a small security team.

2
Splunk vs Sentinel — Key Trade-offs

Splunk excels in flexibility, on-premises deployment options, and environments with diverse, complex log sources requiring heavy custom parsing. Its SPL language is arguably more powerful than KQL for complex analytics. Sentinel excels in Microsoft-ecosystem integration, cloud-native architecture, and consumption-based pricing that favours lower-volume deployments. For maritime organisations starting fresh with a Microsoft 365 foundation, Sentinel is typically faster and cheaper to deploy. For organisations with existing Splunk infrastructure or mixed-vendor environments, Splunk ES is often the better fit.

3
Maritime OT Monitoring with Splunk

The Splunk App for OT Security (built on Splunk with add-ons for common OT protocols — Modbus, DNP3, IEC 61850) provides monitoring capabilities for industrial control systems. OT Add-ons parse protocol-level telemetry from OT network sensors. For maritime vessels, Splunk's OT capabilities, combined with passive OT network monitoring sensors (Claroty, Nozomi, or similar) that forward data to Splunk, provide the foundation for vessel-level security monitoring that bridges IT and OT telemetry in a single platform.

✍️ Author Insight — From the Field
Captain Paul · Maritime Cybersecurity Consultant · IACS UR E26/E27

During E26 CRSI assessments of larger shipping companies, Splunk is frequently already deployed for IT operations — used for application performance monitoring, log search, and troubleshooting rather than security. This creates an interesting situation: the platform infrastructure exists, but it has not been configured for security use cases. No correlation searches are enabled. No security dashboards exist. The Splunk deployment that could be a security monitoring platform is being used as an expensive log archive. Converting an existing Splunk deployment into a functioning security monitoring tool — enabling Splunk ES, activating and tuning the built-in correlation searches, deploying vessel-specific searches — is typically far faster and cheaper than deploying a new SIEM from scratch. If you have Splunk, activate the security capabilities before you evaluate buying something new.

Practical first step: The Splunk Security Essentials app (free in Splunkbase) provides a library of over 300 pre-built security searches mapped to MITRE ATT&CK. Install it, run the Data Security Posture assessment to see which searches your current data sources support, and activate the highest-priority searches for your environment. This is the fastest path from 'Splunk installed' to 'security monitoring active'.

✅ Key Takeaways — Lesson 19
  • Splunk's distributed architecture (Forwarders → Indexers → Search Heads) enables flexible, scalable deployment from a single server to a global enterprise — including maritime vessel-to-shore forwarding architectures.
  • SPL (Search Processing Language) is Splunk's powerful query language, enabling complex log analysis, aggregation, correlation, and visualisation for security investigation and detection.
  • Splunk Enterprise Security (ES) adds the security operations layer: Notable Events, Risk-Based Alerting, Correlation Searches, the Asset/Identity Framework, and Threat Intelligence Management.
  • Risk-Based Alerting (RBA) dramatically reduces alert volume by accumulating risk scores rather than generating individual alerts for each low-confidence detection — critical for managing SOC alert fatigue.
  • Splunk SOAR provides automated playbook execution for tier-1 triage, freeing analysts for investigation and judgement rather than repetitive enrichment and notification tasks.
  • For maritime OT monitoring, Splunk's OT Security add-ons combined with passive OT network sensors provide the most mature pathway to combined IT/OT security visibility in a single platform.
