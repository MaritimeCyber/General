Detection Engineering for Maritime OT

Captain Paul
Maritime Cybersecurity · IACS UR E26/E27
September 2026
🎯 Lesson Objective

After this lesson you can apply detection engineering principles to maritime OT environments, write detection rules for maritime-specific attack techniques (NMEA anomalies, Modbus irregularities, AIS spoofing indicators), understand the data model differences between IT and OT detection, explain how passive OT network monitoring tools (Claroty, Nozomi) integrate with SIEM for detection, and describe what a maritime OT detection use case library looks like.

Detection engineering for maritime OT builds on the general detection engineering principles covered in Lesson 23, but faces unique challenges that require maritime-specific adaptations. Enterprise IT detection rules look for Windows event IDs, PowerShell command patterns, network connection anomalies. Maritime OT detection rules look for NMEA sentence anomalies, Modbus register access outside expected patterns, AIS message irregularities, and network connections between vessel segments that should never communicate.

The data model is different. Where enterprise IT detection works with structured Windows event log data, authentication logs, and process telemetry, maritime OT detection works with decoded protocol frames from industrial and maritime communication standards — NMEA 0183, NMEA 2000, Modbus RTU/TCP, IEC 61162. The fields that matter are maritime-domain-specific: sentence type codes, message field values, register addresses, function codes. A detection engineer building maritime OT rules must understand both the protocol semantics and the operational context to write rules that are both accurate and low-noise.

The tooling is also different. OT-specific network monitoring platforms (Claroty, Nozomi Networks, Dragos) provide the protocol decode capability and the baseline learning that SIEM platforms cannot. These tools feed structured OT events to the SIEM, where detection rules can then be applied. The detection engineering workflow for maritime OT is typically: OT sensor (decode) → OT platform (baseline, alert) → SIEM (correlate with IT events, case management). Understanding this toolchain is the foundation for maritime OT detection engineering.

1. Maritime OT Protocol Detection Fundamentals

1. Maritime OT Protocol Detection Fundamentals
1
NMEA 0183 Anomaly Detection

NMEA 0183 sentences are the standard data format for maritime navigation sensors. Each sentence has a defined structure: talker identifier, sentence type, comma-separated data fields, and checksum. Valid sentences have known talker codes (GP for GPS, GL for GLONASS, RA for radar), known sentence types ($GPGGA for GPS fix data, $GPRMC for recommended minimum data, $AISRM for AIS received messages), and field values within operational ranges (latitude -90 to 90, longitude -180 to 180, speed 0 to 30 knots for most commercial vessels). Detection rules for NMEA anomalies: field values outside valid operational ranges, unexpected talker/sentence combinations, sentences with invalid checksums (potential injection), and position updates with speed-of-change impossible for the vessel type.

2
Modbus Detection Patterns

Modbus is the dominant communication protocol in vessel engine and machinery OT systems. Detection patterns: function code 8 (Diagnostics) executed during normal operation (used for testing, suspicious during operations), write operations (function codes 5, 6, 15, 16) to registers not in the documented write-permitted list, read operations to registers not in the normal polling sequence, and Modbus traffic from IP addresses not in the documented engineering workstation list. Write operations to safety relay registers (over-speed trip, high-temperature shutdown) are the highest-severity detection: these registers should never receive write commands from IT-network IP addresses.

3
Network Segmentation Violation Detection

The most impactful maritime OT detection rule is also the simplest: any accepted network connection from an IT segment IP range to an OT segment IP range that is not in the documented exception list. This rule fires on lateral movement attempts, firewall misconfigurations that create IT-to-OT paths, and malware that scans across segments after compromising an IT host. Implementation: export the firewall accept logs to the SIEM, define the IT and OT IP ranges as lookup tables, and alert on any accepted flow where source is in IT range and destination is in OT range and the connection is not in the approved exception list.

4
AIS Anomaly Detection

AIS message anomaly detection requires access to the vessel's received AIS data stream. Suspicious patterns: vessels transmitting AIS with MMSI numbers that do not match the vessel's registered data (potential spoofing), AIS position reports that place a vessel at a physically impossible location given its last known position and elapsed time, multiple vessels transmitting with the same MMSI (MMSI collision, possibly indicative of AIS spoofing for sanctions evasion), and AIS messages with vessel name or call sign fields containing anomalous characters or lengths.

2. OT Platform Integration and SIEM Detection

2. OT Platform Integration and SIEM Detection
1
Claroty and Nozomi Integration

Claroty and Nozomi Networks are the leading OT security platforms for maritime deployments. Both deploy passive network sensors on OT network SPAN ports, decode OT protocols (including maritime-specific protocols), learn baselines of normal communication patterns, and generate structured events and alerts. Both integrate with major SIEM platforms (Microsoft Sentinel, Splunk) via API or syslog connectors, forwarding decoded OT events and platform alerts to the SIEM for correlation with IT events and centralised case management. The SIEM receives: Claroty/Nozomi alert events (pre-classified by the OT platform), OT protocol events (decoded Modbus, NMEA, IEC 61162 frames), and asset inventory updates (new devices detected on the OT network).

2
Dragos for Maritime ICS

Dragos is an ICS-focused security platform with deep ATT&CK for ICS integration. The Dragos platform provides: OT asset discovery (identifying every device on the OT network and its protocol profile), threat detection (pre-built detections for ICS-specific attack techniques mapped to ATT&CK for ICS), investigation workflow (ICS-aware incident investigation tools), and threat intelligence (the Dragos WorldView intelligence feed covers ICS-targeted threat groups). For maritime operators building a mature OT detection programme, Dragos provides the ICS-specific intelligence and detection content that general-purpose OT monitoring tools lack.

3
SIEM Correlation — IT and OT Events

The most powerful maritime detection engineering occurs at the IT/OT correlation layer in the SIEM: correlating an IT event (suspicious logon to a vessel workstation) with an OT event (Modbus write to an engine safety register 10 minutes later) into a single incident that tells the story of lateral movement from IT to OT. This correlation requires: (1) both IT and OT events in the same SIEM, (2) a common time synchronisation source (NTP) ensuring that IT and OT event timestamps align, and (3) correlation rules that bridge the IT and OT event namespaces. Building these correlation rules is the pinnacle of maritime OT detection engineering.

4
Data Normalisation for OT Events

OT events from passive monitoring sensors are not natively compatible with SIEM data models. Maritime OT detection engineering requires custom data normalisation: mapping NMEA talker/sentence codes to SIEM field names, mapping Modbus function codes and register addresses to descriptive names, and defining vessel-specific asset identifiers (vessel name, IMO number) that link OT events to the correct vessel context in the SIEM. This normalisation work is unglamorous but essential — detection rules written against normalised OT data are readable, maintainable, and transferable across vessel deployments.

3. Maritime OT Detection Use Case Library

3. Maritime OT Detection Use Case Library
1
Priority 1 — Safety System Integrity

Detection rules that protect safety-critical systems have the highest priority. These include: any write command to safety relay registers (over-speed trip, emergency shutdown, CO2 suppression activation) from unauthorised IP addresses; ECDIS application process termination outside scheduled maintenance windows; loss of primary GPS signal without switchover to backup source; and navigation system alarm suppression events (an attacker who has accessed a navigation system may suppress alarms to hide anomalies from the crew).

2
Priority 2 — IT/OT Boundary Violations

Detection rules that identify IT-to-OT lateral movement: accepted firewall connections from IT to OT segments not in the exception list; new IP addresses appearing on the OT network switch not in the asset inventory; ECDIS or engine management system making outbound internet connections not via the approved update paths; and Modbus traffic from IP addresses not in the engineering workstation list.

3
Priority 3 — Access and Authentication Anomalies

Detection rules for access control violations: VSAT management interface logon from non-whitelisted IPs; ECDIS system access using shared or administrative credentials rather than individual officer credentials; remote access VPN sessions active to OT network segment IP ranges outside scheduled maintenance windows; and multiple simultaneous remote access sessions to the same OT system from different geographic locations (credential sharing or compromise indicator).

✍️ Author Insight — From the Field
Captain Paul · Maritime Cybersecurity Consultant · IACS UR E26/E27

During E26 CRSI assessments that include OT detection engineering reviews, the most common finding is that the detection rules that exist — if any exist — are all IT rules applied to IT systems, with zero detection content for vessel OT systems. The shore-based SIEM may have Sentinel analytics rules for Windows Security events; it has nothing for ECDIS behaviour, nothing for Modbus anomalies, nothing for AIS data integrity. This is not a sophisticated detection gap — it is an absence of detection. Building even the Priority 1 safety system integrity detections described above — five rules, all straightforward, all based on data that is already flowing from the OT monitoring sensor — would represent the largest single improvement to vessel security detection capability that most assessments encounter. Detection engineering for maritime OT does not require exotic skills; it requires maritime domain knowledge applied to basic detection engineering principles.

Practical first step: Identify one OT system on one vessel that currently has an available log or event output — most likely the VSAT router, the vessel firewall, or the ECDIS event log. Define three detection rules for that system: one for administrative access anomalies, one for unexpected connections, one for process or configuration change events. Implement those three rules in your SIEM. You now have maritime OT detection capability where you had none. Iterate one system at a time until you have coverage across all critical vessel systems.

✅ Key Takeaways — Lesson 32
  • Maritime OT detection rules work with protocol-specific data — NMEA sentence fields, Modbus function codes and register addresses, AIS message fields — requiring maritime domain knowledge to write effectively.
  • The highest-impact maritime OT detection rule is IT-to-OT network segmentation violation monitoring: any accepted firewall connection from IT to OT segments not in the documented exception list.
  • OT platforms (Claroty, Nozomi, Dragos) decode maritime protocols, learn baselines, and forward structured events to the SIEM — the detection engineering layer sits in the SIEM, not in the OT platform itself.
  • IT/OT correlation in the SIEM — correlating a suspicious IT logon with an OT Modbus write 10 minutes later — is the most powerful maritime detection capability, requiring common time synchronisation and custom correlation rules.
  • Maritime OT detection use cases are prioritised: safety system integrity (Priority 1), IT/OT boundary violations (Priority 2), access and authentication anomalies (Priority 3).
  • Data normalisation — mapping OT protocol fields to SIEM schemas, defining vessel-specific asset identifiers — is the prerequisite engineering work that makes maritime OT detection rules maintainable and transferable.
