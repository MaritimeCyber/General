Security Analytics and Detection Validation

Captain Paul
Maritime Cybersecurity · IACS UR E26/E27
September 2026
🎯 Lesson Objective

After this lesson you can explain what security analytics adds beyond rule-based detection, describe UEBA (User and Entity Behaviour Analytics) and its role in detecting insider threats and compromised accounts, explain Breach and Attack Simulation (BAS) and how it validates detection coverage, and understand how continuous validation is applied in a maritime fleet monitoring context.

Detection rules answer a specific question: 'Has this specific thing happened?' Security analytics asks a broader question: 'Is anything happening here that is unusual, anomalous, or statistically inconsistent with what this user or system normally does?' The distinction is between known-threat detection (rules) and unknown-threat discovery (analytics). Both are necessary; neither alone is sufficient.

Rules fail when attackers know them and avoid the patterns they detect. Analytics fail when the attacker's behaviour is statistically similar to normal (slow-and-low approaches, using legitimate credentials). The most mature detection programmes use both: rules for known-pattern detection, analytics for anomaly discovery, and human judgement for the synthesis of both into accurate threat assessment.

Detection validation — the practice of testing whether detection rules actually fire when the techniques they target are executed — is the quality control layer for both rules and analytics. Without validation, a detection programme is built on assumptions: 'We have a rule for this technique, therefore we detect it.' Validation converts assumptions into evidence — actually executing the technique, in the environment, and confirming the detection fires.

1. Security Analytics and UEBA

1. Security Analytics and UEBA
1
User and Entity Behaviour Analytics (UEBA)

UEBA establishes statistical baselines of normal behaviour for each user and device (entity) in the environment. Normal behaviour for a vessel officer: logon from the vessel IP range, access to navigation applications, email usage during watch hours. An anomaly: logon from a previously unseen IP at 03:00, access to the HR system, large data download. UEBA scores these deviations from baseline and generates alerts when accumulated anomaly scores exceed a threshold, even without a matching rule.

2
Insider Threat Detection

UEBA is the primary tool for detecting insider threats — employees or contractors who abuse legitimate access. An insider's credentials are valid, their initial access is authorised, and their actions may individually look legitimate. But the pattern of access — accessing systems they never access, downloading unusually large volumes of data, working at unusual hours before a resignation — is detectable as a statistical anomaly even when each individual action is not policy-violating in isolation.

3
Machine Learning Detection Models

Beyond UEBA, machine learning models are used for: network traffic anomaly detection (models trained on normal traffic patterns that flag deviations), email security (models that classify phishing emails based on content, sender reputation, and recipient behaviour), and log anomaly detection (models that flag unusual sequences of log events in process execution chains). ML models complement rules by detecting threats in the 'long tail' — techniques and variants that have not yet generated specific detection rules.

4
Analytics Limitations

Analytics models have two failure modes: false negatives (the attacker's behaviour looks 'normal') and false positives (legitimate unusual behaviour that looks like an attack). A new employee accessing systems they have never accessed before triggers UEBA false positives. A sophisticated attacker who studies the baseline and deliberately stays within normal parameters evades UEBA detection. Analytics are not a replacement for rules — they are a complementary detection layer.

2. Breach and Attack Simulation (BAS)

2. Breach and Attack Simulation (BAS)
1
What is BAS?

Breach and Attack Simulation (BAS) platforms (Cymulate, AttackIQ, SafeBreach, Picus Security) automatically execute simulated attack techniques — safe versions of real ATT&CK techniques that do not cause damage but produce the same telemetry as the real attack — and check whether the detection controls (SIEM rules, EDR, email gateway) generate the expected alerts. BAS converts the question 'would we detect this attack?' from a theoretical assumption into an empirical measurement.

2
Continuous Validation

Unlike a penetration test (performed annually or quarterly), BAS runs continuously — executing the same validation tests every day or week. Any change to the environment that breaks a detection (a SIEM rule update that introduces a syntax error, a log source that stops sending data, an EDR policy change that disables a detection) is immediately identified and flagged. Continuous validation ensures that the detection coverage that exists today still exists tomorrow.

3
ATT&CK Coverage Measurement

BAS platforms report detection coverage as a percentage of ATT&CK techniques tested that generate a detection alert. This provides an objective, empirical measurement of detection coverage that can be tracked over time and reported to security leadership. Improving the ATT&CK coverage score from 40% to 70% over six months is a concrete, measurable security improvement — not a subjective 'we have improved our security posture' claim.

4
Maritime BAS Considerations

Standard BAS platforms test enterprise IT attack techniques. Maritime-specific validation requires: (1) Testing detection rules for maritime-specific scenarios (ECDIS process anomaly, OT network lateral movement) using custom test cases or OT-capable BAS platforms. (2) Testing detection coverage from the vessel perspective — running validation tests from a vessel-representative network segment to confirm that telemetry transmission over VSAT does not introduce delays or packet loss that affects detection latency. (3) Validating that detection rules that work in the lab also fire on real vessel hardware.

3. Building a Maritime Validation Programme

3. Building a Maritime Validation Programme
1
Validation Test Library

A maritime validation test library covers: phishing simulation (email delivery, user click tracking, payload execution on vessel workstations), endpoint protection validation (safe ATT&CK technique execution on vessel workstations using Atomic Red Team), network detection validation (safe network scanning and lateral movement simulation on vessel network segments), and OT-specific validation (safe simulation of OT protocol anomalies — unusual Modbus commands, unexpected NMEA sentence injection — in a test environment representative of vessel OT systems).

2
Purple Team Exercises as Validation

For maritime operators without a BAS platform, structured purple team exercises provide manual validation. The red team executes a specific ATT&CK technique (under controlled conditions, on representative systems); the blue team confirms whether the detection fired. Documenting every technique tested, whether it generated a detection, and what improvement is required produces a validation report that serves the same function as an automated BAS scan.

3
Reporting Detection Programme Maturity

Detection programme maturity is reported through a dashboard: ATT&CK coverage score (% of techniques with validated detection), false positive rate per rule, MTTD per technique category, open detection gaps (techniques in the threat model with no validated coverage), and rule health (rules that failed most recently in validation). This dashboard provides security leadership with a quantitative view of the organisation's detection capability — and a prioritised improvement backlog.

✍️ Author Insight — From the Field
Captain Paul · Maritime Cybersecurity Consultant · IACS UR E26/E27

During E26 CRSI assessments, the question 'would you detect an attack on your vessels?' is almost always answered with a confident 'yes' — before the data is examined. After examining the data — no vessel telemetry in the SIEM, no detection rules active for vessel systems, no testing of detection capability ever conducted — the honest answer becomes 'we would not know'. Introducing BAS or purple team validation into a maritime security programme is the single most effective way to convert a 'we believe our detection works' assumption into 'we have tested our detection and it catches X% of the techniques we care about'. The number that comes back from the first validation run is almost always a shock — and a powerful catalyst for investment in detection engineering.

Practical first step: Run the MITRE ATT&CK Evaluations emulation plans (freely available at attackevals.mitre.org) as a manual purple team exercise. Pick the evaluation most relevant to your threat model (APT29 for espionage threats, Carbanak/FIN7 for financially-motivated attackers). Execute the emulation steps on a test vessel workstation. Count how many steps generated a detection alert. Divide by total steps. That is your detection coverage percentage — and your improvement target.

✅ Key Takeaways — Lesson 24
  • Security analytics (UEBA, ML models) detects unknown threats through statistical anomaly identification rather than known-pattern matching — complementing rule-based detection rather than replacing it.
  • UEBA establishes individual user and entity behavioural baselines, alerting on statistical deviations that may indicate compromised accounts, insider threats, or novel attack techniques.
  • BAS platforms continuously execute safe simulations of ATT&CK techniques and measure whether detection controls respond — converting 'would we detect this?' from assumption to empirical measurement.
  • Continuous validation (daily or weekly BAS execution) catches detection regressions immediately: SIEM rule changes, log source failures, or EDR policy modifications that break detection coverage.
  • ATT&CK coverage score — the percentage of in-scope techniques with validated detection — is the key detection programme metric for reporting to security leadership.
  • Maritime validation requires OT-specific test cases and vessel-representative network testing to confirm that detection coverage demonstrated in lab conditions translates to real vessel deployments.
