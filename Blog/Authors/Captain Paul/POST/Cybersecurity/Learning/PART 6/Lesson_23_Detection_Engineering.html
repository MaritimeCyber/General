Detection Engineering

Captain Paul
Maritime Cybersecurity · IACS UR E26/E27
September 2026
🎯 Lesson Objective

After this lesson you can define detection engineering and distinguish it from writing ad-hoc detection rules, describe the detection engineering lifecycle from hypothesis to production rule, explain the Sigma rule format and how it enables vendor-agnostic detection sharing, understand detection quality metrics (precision, recall, MTTD), and describe how a maritime detection rule library is structured around ATT&CK for ICS.

Writing a detection rule is easy. Writing a detection rule that fires reliably on real attacks, almost never fires on legitimate activity, stays current as the environment changes, and is documented well enough that a new analyst can understand what it does and why — that is detection engineering. The difference between ad-hoc rule writing and detection engineering is the same as the difference between writing a one-off script and writing production software: discipline, process, and quality standards.

Detection engineering applies software engineering principles to the creation and maintenance of detection content. Rules are written to specification, tested before deployment, version-controlled, documented, reviewed, and retired when no longer relevant. The detection content library is treated as a product that requires continuous investment — new rules for new threats, tuning for changed environments, retirement of rules for deprecated systems.

For maritime cybersecurity, detection engineering is particularly important because the detection content that ships off-the-shelf in SIEM platforms is built for enterprise IT environments — it has no awareness of ECDIS, AIS, vessel network architecture, or maritime attack patterns. Building a maritime-specific detection library, from hypothesis through production rule through quality validation, is a core capability for any organisation managing vessel cybersecurity at scale.

1. The Detection Engineering Lifecycle

1. The Detection Engineering Lifecycle
1
Threat Model and Hypothesis

Detection engineering starts with a threat model — a prioritised list of threats relevant to the organisation's environment. In maritime, the threat model includes ransomware via phishing, credential theft via exposed management interfaces, GPS spoofing, and supply chain compromise of navigation software update mechanisms. Each threat generates hypotheses: 'If ransomware is executing on a vessel workstation, what behaviours will it exhibit? Mass file encryption, shadow copy deletion, ransom note creation, C2 beaconing.' Each behaviour becomes a detection candidate.

2
Rule Development and Testing

Detection rules are developed against real or simulated log data that represents the technique being detected. Atomic Red Team (a library of open-source ATT&CK technique tests) and similar tools provide safe, controlled technique execution for testing detection rules against real telemetry. A rule is tested for: true positive rate (does it fire when the technique is executed?), false positive rate (does it fire on normal activity?), performance impact (does the query run within the SIEM's time constraints?).

3
Staging and Production Deployment

Rules move through environments before production: Development (rule written, unit-tested against synthetic data) → Staging (rule deployed in alert-only mode in the live environment, monitored for false positives) → Production (rule deployed with alerting enabled, analyst playbook updated). Each stage has a gate: minimum time in staging with observed false positive rate below threshold before promotion to production.

4
Rule Maintenance and Retirement

Detection rules require maintenance: environment changes (new systems added, IP ranges changed, user behaviour patterns shifted) cause rules that worked at deployment to false-positive on legitimate activity. A mature detection engineering programme monitors rule performance continuously — tracking alert volume, false positive rate, and time-to-analyst-action for each rule — and schedules quarterly reviews to tune, update, or retire underperforming rules.

2. Sigma — Vendor-Agnostic Detection Rules

2. Sigma — Vendor-Agnostic Detection Rules
1
What is Sigma?

Sigma is an open standard for writing detection rules in a vendor-agnostic format. A Sigma rule describes a detection logic in YAML: the log source (Windows Security Event Log, Syslog, Web Server logs), the detection condition (specific field values and their relationships), and metadata (title, description, ATT&CK mapping, severity, tags). Sigma rules are converted to platform-specific query formats — KQL for Microsoft Sentinel, SPL for Splunk, YARA-L for Google SecOps — by a compiler (pySigma or sigmac).

2
Why Sigma Matters

Sigma enables detection rule sharing across the security community. The SigmaHQ repository on GitHub contains thousands of community-contributed detection rules mapped to ATT&CK techniques — a free library of production-ready detection content maintained by security engineers globally. A maritime operator who implements a Sigma-compatible SIEM can import this rule library and immediately deploy detection coverage for hundreds of ATT&CK techniques, without writing rules from scratch.

3
Writing Maritime Sigma Rules

Maritime-specific Sigma rules detect vessel-specific attack scenarios: VSAT management interface logon from non-whitelisted IPs (log source: firewall, condition: destination=VSAT_MGMT_IP, source not in WHITELIST), ECDIS process unexpected child process spawn (log source: Sysmon process creation, condition: ParentImage=ecdis.exe AND Image not in allowed_children), USB storage device insertion on bridge workstation (log source: Windows Security, condition: EventID=6416, DeviceType=USB storage).

4
Detection-as-Code

Detection-as-code applies DevOps practices to detection content management: detection rules stored in version-controlled repositories (Git), tested automatically in CI/CD pipelines (automated false-positive testing against synthetic benign data), deployed to SIEM platforms via API rather than manual configuration. This approach enables large-scale detection programmes to maintain quality and version history across thousands of rules without manual tracking.

3. Detection Quality Metrics

3. Detection Quality Metrics
1
Precision and Recall

Precision measures the fraction of alerts that are true positives (low false positive rate = high precision). Recall measures the fraction of real attacks that generate alerts (missing no attacks = high recall). The goal is high precision AND high recall — rules that catch all real attacks and generate no false positives. In practice, there is a trade-off: very sensitive rules catch everything but generate excessive false positives (low precision); very specific rules have few false positives but miss attacks (low recall). Tuning rules moves them toward the optimal point in the precision-recall space.

2
MTTD and Rule Coverage

Mean Time to Detect (MTTD) is the time between an attacker executing a technique and an alert being generated. Lower MTTD means earlier detection and less time for the attacker to cause damage. ATT&CK coverage measures what percentage of the ATT&CK matrix generates at least one detection rule — ideally every technique relevant to the threat model has coverage. Both metrics are tracked in a detection programme dashboard and reported to security leadership as indicators of programme maturity.

3
False Positive Impact

Each false positive alert costs analyst time — typically 10-30 minutes to triage, investigate, and close. At scale, a rule with a 5% false positive rate on an environment generating 10,000 events/hour can create 500 false positive alerts per hour. The direct cost is analyst time; the indirect cost is alert fatigue, which causes analysts to dismiss alerts without thorough investigation. False positive management is not optional — it is a prerequisite for a functioning detection programme.

✍️ Author Insight — From the Field
Captain Paul · Maritime Cybersecurity Consultant · IACS UR E26/E27

During E26 CRSI assessments, detection engineering programme maturity varies enormously. At one extreme: organisations with no detection rules at all — their SIEM is collecting logs but no rules are enabled, because 'we have not had time to configure it yet'. At the other extreme: organisations with hundreds of active rules, a Sigma-based detection-as-code pipeline, and a documented quarterly review process. For maritime operators at the low end, the starting point is not to build a detection engineering programme from scratch — it is to deploy the vendor-provided content packs (Microsoft Sentinel solutions, Splunk Security Essentials), review and tune the highest-priority rules for the maritime environment, and build the programme discipline around that foundation. A detection programme with 20 well-tuned, maritime-relevant rules is more valuable than 500 generic rules with 30% false positive rates that the SOC has learned to ignore.

Practical first step: Map your current active detection rules to the MITRE ATT&CK matrix using the ATT&CK Navigator. Colour each technique covered by an active, tuned rule in green. The result is your detection coverage map. Prioritise the red cells (no coverage) that correspond to the techniques most used by threat actors targeting maritime organisations — those are your detection engineering backlog.

✅ Key Takeaways — Lesson 23
  • Detection engineering applies software engineering discipline — specification, testing, staging, versioning, maintenance — to the creation and lifecycle management of detection rules.
  • Rules progress through Development → Staging (alert-only, false-positive monitoring) → Production (alerting enabled) with quality gates at each stage.
  • Sigma is an open standard for vendor-agnostic detection rules that enables sharing across the security community and deployment across multiple SIEM platforms from a single rule source.
  • Maritime-specific Sigma rules focus on VSAT interface anomalous access, ECDIS process integrity, USB insertion on bridge workstations, and OT network unexpected traffic patterns.
  • Detection quality metrics — precision, recall, ATT&CK coverage, and MTTD — measure detection programme maturity and should be reported regularly to security leadership.
  • Detection-as-code (rules in Git, tested in CI/CD, deployed via API) is the operational model for managing detection libraries at scale without sacrificing quality or version history.
