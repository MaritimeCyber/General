Threat Hunting

Captain Paul
Maritime Cybersecurity · IACS UR E26/E27
September 2026
🎯 Lesson Objective

After this lesson you can define threat hunting and distinguish it from alert-based incident detection, describe the hypothesis-driven hunting methodology, explain how the MITRE ATT&CK framework drives hunting hypotheses, identify the data sources and tools used in threat hunting, and understand how maritime-specific threat hunting hypotheses are constructed for vessel OT environments.

Detection rules and SIEM alerts are reactive: they fire when an attacker's technique matches a known pattern. But sophisticated attackers know which patterns are being detected, and they specifically craft their campaigns to avoid them. Living-off-the-land techniques (using legitimate system tools), encrypted command-and-control traffic, and slow-and-low data exfiltration are all designed to fall below the detection threshold. A threat hunter's job is to find these attackers proactively — before they cause damage, before an alert fires.

Threat hunting starts from a hypothesis: 'What if a threat actor with these capabilities has already compromised our environment? What evidence would that leave?' The hunter then goes looking for that evidence across available log data and endpoint telemetry, using knowledge of attacker TTPs and the specific characteristics of the organisation's environment. Finding the evidence confirms the hypothesis and begins an incident response. Finding no evidence either means the hypothesis was wrong (no attacker with those capabilities is present) or the data needed to test it is not available — also an important finding.

In maritime cybersecurity, threat hunting is particularly valuable because vessel environments are likely to have poor baseline visibility and long dwell times. An attacker who compromised a vessel's navigation system software update mechanism might have been present for months before any alert fired — if any alert fired at all. A threat hunt specifically looking for evidence of supply chain compromise in update processes would detect this long before the attacker chose to act.

1. The Threat Hunting Process

1. The Threat Hunting Process
1
Hypothesis Generation

Every threat hunt starts with a hypothesis — a specific, testable statement about attacker behaviour. Good hypotheses are driven by: (1) Threat intelligence ('APT group X targeting maritime organisations has been observed using T1059.001 PowerShell execution to download second-stage payloads') — hunt for evidence of that specific technique in your environment. (2) Organisational context ('Our VSAT management interface is externally accessible; an attacker who compromised it would need to perform discovery to map the internal network') — hunt for discovery activity from the VSAT management system IP. (3) Security control gaps ('We have no EDR on engine room workstations') — hunt for signs of compromise on the systems that lack visibility.

2
Data Collection and Analysis

With a hypothesis defined, the hunter identifies which data sources contain evidence relevant to that hypothesis, queries them using the SIEM search language (KQL, SPL, or similar), and examines the results. Effective hunting requires high-fidelity telemetry: process execution logs with command-line arguments, network connection logs with DNS resolution data, authentication logs with source IP and user-agent. Data that has not been collected cannot be hunted — improving data collection is a key output of threat hunting programmes.

3
Hunt Output — True Positives and Improvements

A successful hunt produces one of two outcomes. A true positive — evidence of malicious activity — initiates the incident response process. A true negative — no evidence found — documents what was searched, confirms the data quality needed to test the hypothesis, and becomes a new detection rule (if this hypothesis is valuable enough to hunt manually, it is valuable enough to automate). Both outcomes have value; a hunt that finds nothing but produces a new detection rule has improved the organisation's security posture.

4
Hunt Teams and Skills

Effective threat hunters combine deep technical knowledge (OS internals, attacker TTPs, SIEM query expertise) with the analytical mindset of an investigator (hypothesis-driven, evidence-based, comfortable with ambiguity). In maritime, hunters also need operational context: understanding what 'normal' ECDIS behaviour looks like, what a legitimate port state control inspection would involve in terms of system access, and what maintenance traffic from authorised third-party vendors looks like on the OT network.

2. Hunting Tools and Data Sources

2. Hunting Tools and Data Sources
1
SIEM as the Primary Hunt Platform

The SIEM is the primary hunting platform, providing historical access to all ingested log data and the search language to query it at scale. A threat hunt against 90 days of endpoint telemetry from a fleet of 20 vessels — looking for evidence of a specific ATT&CK technique — would involve querying billions of events in the SIEM's data lake. Proficiency with the SIEM's search language (KQL, SPL, or similar) is the foundational skill for any threat hunter.

2
EDR Telemetry

EDR platforms provide the richest endpoint telemetry for threat hunting: process execution trees (what spawned what), file system operations, network connections with resolved DNS names, memory operations (including injection attempts), and credential access events. EDR-native hunt tools (CrowdStrike Falcon Insight, SentinelOne's hunting interface) provide optimised query interfaces for hunting across endpoint data without requiring full SIEM ingestion.

3
Network Traffic Analysis

Network-level hunting uses flow data (NetFlow, IPFIX — source/destination IP, port, bytes transferred, duration) and full packet capture (where storage permits) to find command-and-control beaconing, data exfiltration, and lateral movement. Beaconing detection — identifying processes that connect to external IPs at regular intervals (a characteristic of C2 malware) — is a powerful hunting technique that works even against encrypted traffic, because the periodicity of the connections is visible in flow data regardless of payload encryption.

4
Threat Intelligence for Hunt Targeting

Threat intelligence narrows the hunt target: which specific indicators (IP ranges, domain patterns, file hashes), which specific techniques (the ATT&CK sub-techniques observed in the latest threat report), and which specific sectors (if maritime-targeted campaigns have been observed) should be prioritised. A threat hunt without intelligence targeting is inefficient — it has an infinite search space. Intelligence-driven hunting focuses the hunt on the highest-probability locations for the most likely threats.

3. Maritime-Specific Hunting Hypotheses

3. Maritime-Specific Hunting Hypotheses
1
Hypothesis: Unauthorised VSAT Interface Access

If an attacker has compromised the VSAT management interface, they would need to access it using either a stolen credential or an exploited vulnerability. Hunt: examine all logon events to the VSAT management interface over the last 90 days. Identify any logons from IP addresses not in the expected shore office or vendor ranges. For each anomalous logon, examine what actions were taken post-authentication — configuration changes, firmware queries, routing table modifications.

2
Hypothesis: Malicious USB Execution on Bridge Workstation

USB-delivered malware is a common vector for vessel compromise (technicians, port agents, crew members with infected drives). Hunt: query EDR telemetry for all processes executed from removable drives over the last 90 days. Examine each result: is the executable signed by a known vendor? Does it spawn child processes or make network connections? Any unsigned executable launched from a USB device on a bridge workstation is high-priority for further investigation.

3
Hypothesis: OT Network Reconnaissance from IT Segment

If an attacker has compromised the vessel IT network and is exploring toward OT systems, they would perform network scanning or SNMP enumeration from the IT segment toward OT IP ranges. Hunt: query firewall and switch logs for any traffic from IT segment IP ranges to OT segment IP ranges that is not explicitly permitted by the firewall ruleset. Any such traffic indicates either a firewall misconfiguration or active lateral movement — both requiring immediate investigation.

✍️ Author Insight — From the Field
Captain Paul · Maritime Cybersecurity Consultant · IACS UR E26/E27

During E26 CRSI assessments, defining the threat hunt programme for a vessel operator almost always starts with the same uncomfortable question: what data do we actually have to hunt in? For most shipping companies, the answer is: Windows event logs from shore-based servers, firewall logs from shore office perimeter devices, and nothing from vessels. A threat hunt programme that has no vessel telemetry cannot find attacker activity on vessels — regardless of how skilled the hunters are. The first recommendation in every assessment with no vessel monitoring is to establish the data collection foundation before investing in advanced hunting capability. A hunter with vessel network flow data and bridge workstation process execution logs can find threats. A hunter with no vessel data can only hunt in the shore office, where the interesting threats are less likely to be.

Practical first step: Start your threat hunting programme with three hunts: (1) Beaconing detection — find all processes making regular external connections at intervals shorter than 5 minutes. (2) PowerShell encoded commands — find all PowerShell executions with base64-encoded arguments. (3) Logon from new IP — find all successful logons from IP addresses not seen in the previous 30 days. These three hunts can be run in any SIEM, require minimal data sources, and have detected real attacker activity in maritime environments.

✅ Key Takeaways — Lesson 22
  • Threat hunting is proactive, hypothesis-driven investigation for threats that have evaded automated detection — it finds attackers before alerts fire rather than responding to alerts after.
  • Hypotheses are generated from threat intelligence (known attacker TTPs), organisational context (specific vulnerabilities and exposures), and security control gaps (systems with no visibility).
  • Effective hunting requires high-quality telemetry: process execution with command-line arguments, network flow data with DNS, and authentication logs with source context.
  • Hunt outputs are binary: a true positive (incident found, IR initiated) or a true negative (hypothesis not confirmed, but a new detection rule created). Both outcomes improve security posture.
  • Maritime-specific hunting hypotheses focus on VSAT management interface access, USB execution on bridge workstations, and lateral movement from IT to OT network segments.
  • Building the vessel telemetry foundation — collecting and centralising vessel log data — is the prerequisite for any meaningful maritime threat hunting programme.
