💡 Insight Article 6 IACS UR E27 Marine Equipment Suppliers

What Should Be Included Within the Scope of Approval or Conformity Verification?

Article 6 of a 12-Part Series on UR E27 Strategies for Marine Equipment Suppliers

※ The product, system, and project examples described in this article are illustrative examples created to explain how the scope of UR E27 approval or conformity verification should be defined and managed.

Blue Horizonist (Lew)
Maritime & Cyber Security Consultant · ISP Consultant

The previous article distinguished among three approaches to responding to UR E27: Type Approval for repeatedly supplied products, project-specific conformity verification of the actual supply configuration, and confirmation of exemption or non-mandatory application. Whichever route is selected, the next step must answer one fundamental question — what exactly will be treated as a single product for the purpose of this approval or conformity verification?

Defining only the product name and Model does not make the approval target sufficiently clear. Even under the same product name, the Hardware Revision, OS, Firmware, Application, Third-Party components, Interfaces, and optional functions may differ.

For example, even if a certificate identifies the product as "Cargo Monitoring System Model A," it may still be difficult to determine whether the actual project supply configuration falls within the approval scope unless the following details are clearly defined:

  • Exact Models and Revisions of the Server and Controllers
  • OS, Firmware, and Application Versions
  • Third-Party Software and major Libraries
  • Included Gateways, Switches, and Engineering Laptops
  • Enabled Ports, Protocols, and Services
  • Whether remote access and Cloud connectivity are included
  • The boundary between the product's internal Network and the vessel Network
  • The Configuration tested during approval
  • Items that may be changed and items requiring reassessment when changed

Defining the approval scope is therefore not simply an exercise in preparing a product list. It means fixing the product's functions, components, Versions, Interfaces, optional functions, and conditions of application as a single verifiable Product Configuration.

This article defines that Product Configuration as the "product Baseline" and examines how it can be managed to prevent discrepancies between the actual project supply configuration and the approval scope.

※ In this article, "approval scope" includes not only the scope of Type Approval but also the scope reviewed by the classification society or shipyard during project-specific conformity verification. The applicable classification society's Rules and Guidance should be consulted to confirm the required submissions and approval procedures. The original IACS UR E27 text and the latest information are available on the official IACS UR E27 page.

1The Approval Scope Is Defined by the Claim Being Demonstrated, Not by the Product's Physical Enclosure

It is easy to understand the approval scope as the equipment contained within a product Cabinet or Panel. From a cybersecurity perspective, however, the scope cannot be determined solely by physical boundaries.

A single Panel may contain components managed by different parties and subject to different responsibilities, including:

  • An Application developed by the equipment manufacturer
  • Third-Party PLCs and Switches
  • A commercial Operating System
  • Antivirus Software provided by the customer
  • Firewall Rules configured by the shipyard
  • Engineering Tools used by field Service Engineers
  • An Interface connected to the vessel's common Remote Access Gateway

Conversely, an Engineering Workstation or Gateway physically located outside the Panel may be difficult to separate entirely from the approval scope if it is essential for changing product settings or performing Software Updates.

The following question should therefore be asked when defining the approval scope:

"Which Hardware, Software, settings, Interfaces, and procedures must be grouped into a single evaluation target to demonstrate that this product satisfies the applicable UR E27 requirements?"

The approval scope is not merely the product's physical boundary. It is the boundary within which the manufacturer can claim conformity and support that claim with Evidence.

2A Product Baseline Must Be Far More Specific Than a Product Name

In this article, a product Baseline means the defined configuration state used as the basis for approval or conformity verification. At a minimum, the product Baseline should cover the following six areas.

Area Key Information to Be Included in the Product Baseline
Hardware Equipment name, manufacturer, Model, Part Number, Revision, and major Modules
System Software OS, Firmware, Driver, Runtime, and Database Versions
Application Product Application, PLC Logic, HMI Project, and configuration file Versions
Third-Party Components Switches, Gateways, Antivirus Software, Libraries, Utilities, and Engineering Tools
Interfaces Physical and logical Interfaces, connected systems, communication direction, Ports, Protocols, and Services
Security Configuration Accounts, privileges, Hardening, Logging, Backup, Update, and remote access settings

The product's functional description, installation Image, Checksum, test procedures, manuals, and support conditions should also be linked to this Baseline.

Completing a product Baseline does not merely mean that a component list has been prepared. It means that the design documents have been developed for that configuration, the security functions have been configured and tested, and the same configuration will be maintained throughout production and delivery.

3Hardware Scope Should Include Supporting Components That Affect Security, Not Only Major Equipment

Manufacturers often define the approved Hardware as major equipment such as Servers, PLCs, and HMIs. The following supporting components, however, may also directly affect the product's cybersecurity:

  • Managed Ethernet Switches
  • Serial-to-Ethernet Gateways
  • USB or SD Card Readers
  • Remote Access Routers
  • External Backup Storage
  • Engineering Laptops
  • Hardware Security Modules
  • Wireless Communication Modules
  • Service Ports
  • Third-Party Network Adapters

For example, an internal Switch may appear to be nothing more than a device that forwards data. If it provides a Web-based management Interface, a Default administrator account, SNMP, Telnet, or Firmware Update functions, it affects both the product's attack surface and its management responsibilities.

Whether Hardware should be included in the approval scope should therefore be determined by the following criteria rather than by its price or relative importance within the product:

  • Is it necessary for the product to perform an essential function?
  • Does it provide or potentially bypass a product security function?
  • Can a user or Service Engineer change its settings?
  • Does it create a connection path to another system?
  • Could its removal or replacement change the test results?
  • Does it require vulnerability and security Update management?

If the answer to any of these questions is yes, the Hardware should either be included in the Baseline or clearly identified as an external dependency.

4Software and Firmware Should Be Managed by Exact Version and Function, Not Merely as "Installed"

A Software inventory stating only "Windows," "Linux," "PLC Firmware," or "HMI Software" is insufficient. Features, Default settings, vulnerabilities, and Log formats can differ depending on the Version and Patch level, even when the product name remains the same.

At a minimum, each Software and Firmware item should be linked to the following information:

  • Product name and manufacturer
  • Version and Build number
  • Patch or Hotfix level
  • Equipment on which it is installed
  • Function performed within the product
  • Installation path or Package identifier
  • Update method
  • Integrity verification method
  • End-of-support date or current support status
  • Whether it is included in the approval scope

For example, recording the OS only as Windows 10 makes it difficult to determine the Edition, Build, security Patch level, and support status. Similarly, a PLC Firmware update may retain the same Major Version while changing its authentication method, communication Services, or security settings through a Minor Version update.

The purpose of managing Versions within the product Baseline is not merely to keep an inventory current. It is to identify which Version was used to design and test the security functions and determine whether the existing test results remain applicable after a Version change.

5PLC Logic, HMI Projects, and Configuration Files Are Also Part of the Application

Conventional Software inventories often include only installed executable files and Packages, while omitting PLC Logic, HMI Projects, and configuration files. In OT products, however, these items may determine the actual operating functions, privileges, communications, and safety-related behavior.

Even when the PLC Hardware and Firmware remain unchanged, a Logic modification may affect:

  • Conditions under which control commands are permitted
  • Input validation
  • Alarm activation criteria
  • Fail-safe behavior
  • Data exchanged with upper-level systems
  • The range of changes that can be made using an Engineering Tool
  • Backup and Restore scope

Changes to an HMI Project may also affect user roles, administrator menus, Alarm presentation, Log generation, and Maintenance screens.

The product Baseline should therefore include:

  • PLC Program or Logic Version
  • HMI Project Version
  • Configuration File Version
  • Date of change and change approver
  • Relationship between the Source and executable versions
  • Build or Compile results
  • Checksum or Hash
  • Applicable test results
  • Differences from the previous Version

It is not enough to state that the "Application Version is unchanged." The manufacturer should also be able to demonstrate that the installed Logic and configuration are identical to those used for testing.

6Third-Party Components Do Not Disappear from the Supply Scope Simply Because the Manufacturer Did Not Develop Them

Not every Hardware and Software component included in a product is developed by the equipment manufacturer. The use of commercial Operating Systems, Switches, Databases, Gateways, Antivirus Software, Open-Source Libraries, and Engineering Tools is common.

However, Third-Party components cannot be excluded from the Baseline and responsibility boundaries merely because they were developed by another supplier. If an equipment manufacturer selects, integrates, and supplies a component as part of its system, it should manage at least the following:

  • Exact product name, Model, and Version
  • Function performed within the product
  • Applied security settings
  • Method for identifying known vulnerabilities
  • Source of Patches and Firmware Updates
  • Compatibility testing method before Updates are applied
  • Manufacturer support period
  • Replacement product selection criteria
  • Tests affected by a component change
  • Certification or approval information for the component itself

Suppose a Third-Party Switch is discontinued and replaced by a similar Model. Even if the Port count and physical dimensions are identical, the Default Services, administrator authentication method, VLAN functions, Log generation capabilities, and Firmware support policies may differ.

A statement such as "may be replaced with an equivalent product" is therefore insufficient. The manufacturer should define in advance which characteristics must remain equivalent for the existing approval and test results to remain valid.

7Open-Source Libraries and Runtimes May Also Need to Be Included in the Baseline

Internal Libraries or Runtimes may change even when the Version of the main Application remains unchanged. Such changes may not create any visible difference in product functionality, but they can have a direct cybersecurity impact.

Typical examples include:

  • Web Server Libraries
  • Cryptographic Libraries
  • Java or .NET Runtimes
  • Database Engines
  • Remote Access Components
  • Logging Frameworks
  • Network Communication Libraries
  • Embedded Linux Packages

For example, even if the Application remains at Version 2.0, a change to the internal OpenSSL Library may affect cryptographic functions, vulnerabilities, and compatibility with other components.

This does not mean that every Library must be listed on the certificate itself. However, components that affect the product's security functions or vulnerability exposure should be traceable through an SBOM or an internal Software component inventory.

The approval scope therefore requires a system capable of managing not only the externally visible Version but also the major dependent Software components that make up that Version.

8Interfaces Are Not Outside the Approval Scope; They Are Essential to Defining Its Boundary

External Interfaces should not be treated merely as matters outside the product when defining the approval scope. Where the product connects to other systems and what communications it permits determine both the product's security design and its division of responsibilities.

Each Interface should be linked to the following information:

  • Physical Interface type
  • Connected system
  • Communication direction
  • Source and Destination
  • Port, Protocol, and Service
  • Data or commands exchanged
  • Authentication and encryption methods
  • Whether the connection is permanent or enabled only when required
  • Whether the communication traverses an untrusted Network
  • Functions that can be modified through the Interface
  • Impact of connection failure or data manipulation
  • Division of responsibilities between the product supplier and the shipyard

For example, if a product supports Syslog forwarding, the product Baseline may include the Log Format, transmission Protocol, configuration method, and Local storage method. The actual receiving Server address, Network path, and vessel-wide retention policy may instead be defined by the project-specific vessel security architecture.

In this case, including the Interface in the approval scope does not mean that every external connection becomes part of the product. It means clearly defining what the product provides and guarantees at the Interface and what conditions must be provided by the vessel.

9Optional and Disabled Functions Must Also Be Addressed Clearly Within the Approval Scope

A product may include functions that can be activated optionally in addition to its basic functions:

  • Remote Access
  • Cloud Data Transmission
  • Wireless Communication
  • USB Updates
  • Web Administration
  • External Log Forwarding
  • Mobile Application Integration
  • Third-Party APIs

Simply marking these functions as "Options" leaves the approval scope unclear. Each function should be classified under one of the following arrangements:

  • 1 Included in the approval scope and tested in an enabled state
  • 2 Included in the approval scope but disabled by Default, with the activation conditions and configuration method verified
  • 3 Excluded from the approval scope and either not installed or made unavailable
  • 4 Added only for a specific project and subject to separate design review and testing

The fact that a Software function exists but is disabled in the user Interface does not necessarily eliminate the attack path. A Background Service, Open Port, or remote call function may still remain active.

Unused optional functions should therefore be checked not only through menu settings but also by confirming that the related Services, Ports, and accounts are actually disabled.

10Including Multiple Models and Versions in One TA Requires a Clear Explanation of Their Commonalities and Differences

A manufacturer may wish to include similar products within a single approval scope. For example, several Models that differ only in Server capacity, display size, or I/O quantity may be managed as one Product Family.

To do so, the manufacturer must demonstrate that the differences among the Models do not affect the security functions or the applicability of the test results.

The following should be reviewed:

  • Common Hardware Architecture
  • Identical OS, Firmware, and Application
  • Identical user authentication and privilege structure
  • Identical Security Log functions
  • Identical Update and Restore methods
  • Identical Network Interfaces and security settings
  • Additional Ports or communication functions available on specific Models
  • Impact of performance differences on security functions
  • Basis for selecting the representative test Model
  • Models that must be excluded or tested separately

For example, a family of HMI products that differs only in display size may reasonably be grouped within one scope. If only the higher-end Model includes a Wireless Module and Remote Access function, however, applying the same security test results to the entire product family may be difficult.

The final scope of the Product Family and the representative test Model should be agreed with the classification society. Before that discussion, however, the manufacturer should be able to explain the common and differentiating elements from a technical perspective.

11A Broader Version Range Is Not Necessarily Better

A manufacturer may wish to describe the approved Software Version as "Version 3.x" or "Version 3.0 and later" to make the approval scope more flexible. Such descriptions are problematic because the functions and security characteristics of future Versions have not yet been verified.

The following factors should be considered when defining a Version range:

  • Criteria distinguishing Major, Minor, and Patch Versions
  • Types of changes permitted within each category
  • Potential changes to security functions and Interfaces
  • Required scope of regression testing
  • Criteria for notifying the classification society or renewing the approval
  • Conditions under which existing Evidence may be reused

Change levels may be classified as follows.

Change Level Example General Response
Patch Change Vulnerability correction or defect fix without functional change Impact analysis followed by limited regression testing
Minor Change Addition of configuration items, Log improvements, or limited Interface changes Reassessment of security functions and related requirements
Major Change Change to the Architecture, authentication method, communication structure, or core functions Full reassessment of the approval scope and test plan

The impact of a change should not be determined automatically from its Version number. A change categorized by the manufacturer as a Patch may still have a Major security impact if it affects authentication or the privilege structure.

What matters is not the Version numbering format but the actual content of the change and its effect on the existing Evidence.

12The Approved Baseline and Project Supply Configuration Should Be Managed Separately and Compared

Even when a product has TA or an established product Baseline, each project has its own supply configuration.

The two concepts can be distinguished as follows:

  • Approved Baseline: The Product Configuration used as the basis for design review and testing during TA or project-specific conformity verification.
  • Project Supply Configuration: The combination of Hardware, Software, settings, and optional functions actually proposed, manufactured, tested, and delivered for a specific vessel.

Once a project begins, the two Configurations should be compared and their differences recorded.

Comparison Item Approved Baseline Project Supply Configuration Difference Action
Server OS Version 1.0 Version 1.1 Patch change Impact analysis and regression testing
Application Version 3.2 Version 3.2 None Apply existing Evidence
Gateway Not included Model G added New Interface Additional design review and testing
Remote Access Disabled Activation required Security boundary changed Agree on approval scope and integration design
Log Integration Syslog supported Connected to central Server Project-specific setting Integration testing
Engineering Laptop Dedicated Laptop Shipyard's shared Laptop Operating condition changed Agree on access control and Service procedures

The purpose of this table is not to classify every difference as a problem. It is to distinguish among differences that can be managed as configuration changes within the existing approval scope, those that require additional testing, and those that may fall outside the approved scope and require consultation with the classification society.

13Evidence Loses Its Validity When the Tested and Delivered Configurations Differ

Even if the product design documents are accurate, the test results may not remain fully applicable when the tested Configuration differs from the delivered Configuration.

Suppose the following Configuration was used during security testing:

  • OS Version 1.0
  • Application Version 3.2
  • Switch Model S1
  • Remote Access disabled
  • Default administrator credentials changed
  • Firewall Rules applied

Problems may arise if the delivery Configuration is changed as follows:

  • An OS Patch is added
  • Switch Model S1 is replaced with Model S2
  • Remote Access is enabled for field support
  • The Default account is recreated during production
  • Firewall Rules are relaxed in response to a communication issue

Each change may appear minor in isolation, but together they create a difference between the tested security state and the actual delivered state.

At a minimum, the following Configurations should therefore be linked and managed:

  • 1 The Configuration used as the basis for design approval
  • 2 The Configuration used for internal security testing
  • 3 The Configuration used during FAT
  • 4 The Configuration manufactured and delivered
  • 5 The final As-Built Configuration handed over after vessel installation

Any differences among these five states should be explainable through change records, impact analyses, and additional testing.

14Document Versions Must Be Consistent for a Product Baseline to Be Valid

A product Baseline cannot be managed through a single Master List alone. Multiple documents must describe the same product state consistently.

The product name, Model, Version, and Interface information should be consistent across the following documents:

  • Product Description
  • Hardware and Software Inventory
  • Network Diagram
  • Interface List
  • Port, Protocol and Service List
  • User and Privilege Matrix
  • Hardening Guide
  • Backup and Restore Procedure
  • Software Update Procedure
  • Vulnerability Management Procedure
  • Test Procedure
  • Test Record
  • Installation Manual
  • Operation and Maintenance Manual
  • Certificate or approval document

For example, the reliability of the product Baseline is weakened if the Network Diagram shows a Remote Access Gateway but the Software Inventory and Test Procedure do not identify the related Agent. The same applies if the test results specify Application Version 3.1 while the delivery list specifies Version 3.2.

Keeping each document individually up to date is not enough. When a product change occurs, the affected documents and test Evidence should be identified and updated together.

15Changes Should Be Classified by Their Security Impact, Not Their Size

When a product change occurs, the manufacturer should first answer the following questions:

  • Does the change affect an approved function or requirement?
  • Does it create a new Interface or access path?
  • Does it alter the account and privilege structure?
  • Does it change any Port, Protocol, or Service?
  • Does it change the type or Format of Security Logs?
  • Does it alter the Software Update or integrity verification method?
  • Does it change the scope of Backup and Restore?
  • Does it introduce a new vulnerability or Third-Party dependency?
  • Can the existing test procedures and results still be applied?
  • Must the classification society or shipyard be notified or asked to approve the change?

Changes may then be classified as follows.

Change Classification Meaning Example Response
Change Within the Approval Scope No material impact on security functions or Interfaces User Interface wording change Internal change record
Impact Assessment Required Certain settings or components have changed OS Patch or replacement with an equivalent Switch Impact analysis and limited retesting
Additional Verification Required Approved security functions or Interfaces are affected Change to Log Format, privileges, or communications Retest the related requirements
Potential Change to Approval Scope The system boundary or core Architecture has changed Addition of Remote Access or Cloud connectivity Consult the classification society and shipyard and consider approval renewal

The manufacturer's internal change categories may differ from the classification society's formal change approval criteria. The internal classification should therefore be used to support the impact analysis and decision-making to be presented to the classification society.

16"Equivalent Replacement" Requires Predetermined Equivalence Criteria

An approved component may need to be replaced because of delivery delays, discontinuation, or supply-chain issues. A replacement should not be treated as equivalent merely because it offers similar performance.

From a cybersecurity perspective, equivalence should include:

  • Identical functions and Interfaces
  • Supported Protocols and Services
  • User authentication method
  • Administrator privileges and Default accounts
  • Log generation and external forwarding capabilities
  • Firmware Update method
  • Backup and configuration restoration functions
  • Available Hardening options
  • Known vulnerabilities and support status
  • Expected support period
  • Compatibility with the existing Network and Application

For example, even if a replacement industrial Switch has the same Port count and processing capacity, it may not be cybersecurity-equivalent if Telnet is enabled by Default, individual user accounts are unsupported, or the Syslog forwarding method differs.

For Third-Party components likely to require replacement, it is therefore advisable to establish equivalence assessment criteria and required regression tests in advance.

17Configuration Freeze Should Occur Before Document Submission

Design approval, procurement, production, FAT, and delivery activities often proceed in parallel. If the product Baseline is finalized too late, the approval documents and the actual product are more likely to diverge.

A Configuration Freeze does not prohibit all subsequent changes. Its purpose is to establish the official product configuration at a defined point and ensure that later changes are managed through an approved process.

In practice, the following stages can be distinguished:

  • Design Baseline Freeze: Finalize the major Hardware, Software, Interfaces, and security functions to establish the basis for design approval documents.
  • Test Baseline Freeze: Finalize the Versions and Configuration to be used for FAT or security testing. If a change occurs during testing, assess its impact and determine the required scope of retesting.
  • Delivery Baseline Freeze: Finalize the installation Image, Firmware, settings, and documents to be delivered.
  • As-Built Baseline: Record the final Configuration handed over after vessel installation and commissioning.

Changes may occur between these Freeze points, but the reason for the change, approver, affected requirements, revised documents, and additional tests should remain traceable.

18What Changes When a Product Baseline Register Is Introduced?

When different departments maintain separate inventories, the Version information for the same product may become inconsistent. To prevent this, it is advisable to maintain a Product Baseline Register that links the approved product configuration to the actual project supply configuration.

Management Item Information to Be Recorded
Product ID Unique identifier for the product or system
Baseline ID Identification number for the approved or project Configuration
Hardware Model, Part Number, Revision, and quantity
Software/Firmware Version, Build, Patch, and installation target
PLC/HMI Logic, Project, and Configuration Versions
Third-Party Component name, Version, supplier, and support status
Interface Connected system, communication direction, Port, Protocol, and Service
Security Configuration Accounts, privileges, Hardening, Logs, Backup, and Remote Access
Approval Reference TA, project-specific verification, or other approval documents
Evidence Reference Design documents, test procedures, and test results
Change History Description, reason, approver, and impact assessment
Project Deviation Differences between the approved Baseline and project supply configuration
Current Status Design, testing, production, delivery, or As-Built

This Register is not simply an asset inventory. It is a management tool that connects the approval scope, product design, test configuration, delivery configuration, and change history through one common reference.

19Six Common Mistakes When Defining the Approval Scope

  • 1 Treating the Product Name as the Approval ScopeMultiple Hardware and Software combinations may exist under the same product name. The Model, Version, and optional functions must also be identified.
  • 2 Including Only Major Equipment While Omitting Gateways and SwitchesEquipment that provides communication paths or management Interfaces may affect the system boundary and attack surface.
  • 3 Assuming That Third-Party Components Are Solely the Supplier's ResponsibilityIf the equipment manufacturer includes and delivers the component as part of its product, it remains responsible for selection, configuration, vulnerability review, and compatibility verification.
  • 4 Treating the Product as Unchanged Because the Application Version Is the SameDifferent PLC Logic, HMI Projects, configuration files, Runtimes, or Libraries may result in different security behavior.
  • 5 Failing to Review Disabled Optional FunctionsRelated Services, Ports, or accounts may remain active even when the function is disabled in the user Interface.
  • 6 Assuming That Configuration Management Ends After FATIP addresses, accounts, Firewall Rules, Software Patches, and remote access settings may change during vessel installation and commissioning. The Configuration should therefore be verified through the As-Built Baseline.

20In Practice, the Approval Scope Can Be Defined in the Following Sequence

  • 1Define the functions and supply scope of the product subject to approval or verification.
  • 2Identify the Hardware, Software, Firmware, and Third-Party components.
  • 3Include PLC Logic, HMI Projects, configuration files, and major Libraries.
  • 4Identify all external Interfaces and optional functions.
  • 5Distinguish the common product scope from project-specific modifications.
  • 6Establish the product Baseline ID and Version rules.
  • 7Link each component to the Requirement–Design–Evidence Matrix.
  • 8Analyze differences between the approved Baseline and project supply configuration.
  • 9Establish Freeze points for the design, test, delivery, and As-Built Configurations.
  • 10Define change classifications, impact assessment criteria, and retesting requirements.
  • 11Agree with the classification society and shipyard on the approval Scope and permitted changes.
  • 12Continuously update the Product Baseline Register and related documents.

Once this process is established, the manufacturer does not need to recreate all Evidence whenever the product changes. It can identify the changed components, affected requirements, and applicable tests and reassess only the necessary scope.

21Conclusion: What Was Approved Was a Specific Configuration, Not a Product Name

One of the most dangerous misconceptions in UR E27 Type Approval or project-specific conformity verification is that the approval scope remains the same whenever the same product name appears.

In practice, the object of conformity verification is a specific Configuration combining the following elements:

  • Hardware and Revisions
  • OS, Firmware, and Application Versions
  • PLC Logic and HMI Projects
  • Third-Party components
  • Network Interfaces
  • Ports, Protocols, and Services
  • User accounts and privileges
  • Logging, Backup, Update, and remote access settings
  • Related manuals and test Evidence
  • Conditions of application and external dependencies

A change to any one of these elements does not necessarily invalidate the approval. However, an existing certificate or test result should not be applied automatically without assessing whether the change affects the security functions, Interfaces, system boundary, or previous test results. The essential element that an equipment manufacturer must manage is therefore not the certificate file itself, but the following chain:

Approved Baseline → Test Configuration → Project Supply Configuration → Delivery Configuration → As-Built Configuration

Existing approvals and Evidence can be relied upon in an actual project only when this chain remains intact.

Defining the approval scope as broadly as possible is not always advantageous. If the manufacturer includes more components and variations than it can effectively manage, maintaining the approval becomes more difficult, and the actual delivered product is more likely to fall outside the approved scope.

A well-defined approval scope is not one that includes the greatest possible number of components. It is one that meets the following conditions:

  • 1The product can be supplied repeatedly in that form.
  • 2Its configuration and Versions can be clearly identified.
  • 3The manufacturer can manage its security functions and Interfaces.
  • 4Its design and test Evidence can be maintained consistently.
  • 5When a change occurs, the manufacturer can assess its impact and take the necessary action.

Only after this product Baseline has been established can the Scope described in the approval documents be aligned with the actual project supply configuration. It also becomes possible to determine whether existing Evidence may continue to be used following a product change.
